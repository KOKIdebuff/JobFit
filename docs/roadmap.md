# HireLink 路线图

## 1. 总体原则

- 优先跑通主闭环。
- 比赛版主线围绕“能力验证”展开，不做功能堆叠型招聘系统。
- P0 必须体现“简历解析 -> 岗位理解 -> 人岗匹配 -> 个性化面试 -> 岗位任务试炼 -> AI 面试证据链报告 -> 成长反馈”的完整逻辑。
- P0 先保证能演示、能讲清楚、能稳定复现。
- 演示数据通过预置数据和受控重置流程维护，不扩展独立维护页面。
- 反作弊不作为当前优先实现功能；MVP 只保留基础面试事件记录，不做可见反作弊判断和强判定。
- P1 再提升体验和可信度。
- P2 才做增强型能力。
- 个人 3-4 周开发周期内，优先选择低风险、可回滚、可替换的实现。
- 第一版优先覆盖 1-2 类岗位，并使用脱敏真实数据做演示。

## 2. 开发优先级

| 优先级 | 模块 | 原因 | 依赖 |
|---|---|---|---|
| P0 | 登录和基础角色权限 | 所有功能的入口，也保护敏感数据；保留演示账号 | 无 |
| P0 | 简历上传与解析 | 后续画像和匹配的输入源 | 用户系统 |
| P0 | 岗位发布与 JD 解析 | 匹配和面试题生成的输入源 | 用户系统 |
| P0 | 职业画像 | 连接简历与后续 AI 流程 | 简历解析 |
| P0 | 人岗匹配 | HR 最核心的筛选能力 | 职业画像、岗位画像 |
| P0 | 面试题生成 | 面试流程的直接驱动 | 简历、岗位、匹配结果 |
| P0 | 岗位任务试炼 | 比赛版最强差异点，用岗位任务验证真实能力 | 岗位画像、匹配结果 |
| P0 | 轻量面试回答记录 | 保留面试闭环，但避免复杂数字人 | 面试题、摄像头权限 |
| P0 | 答后 ASR 转写 | 把回答转成 HR 和 AI 可读文本，MVP 使用浏览器 Web Speech API | 回答记录、浏览器权限 |
| P0 | AI 面试证据链报告 | 最终价值输出，需要包含评分、回答证据、任务表现证据和成长建议 | 回答文本、任务试炼结果、画像、岗位信息 |
| P0 | HR 工作台 | HR 侧展示和决策入口 | 匹配、报告 |
| P0 | 求职者报告 / 反馈中心 | 学生侧成长闭环 | AI 面试证据链报告 |
| P0 | 多 Agent 协作展示 | 答辩时说明系统内部如何分工协作 | 解析、匹配、面试、评价流程 |
| P0 | 演示预置数据 | 降低比赛现场失败风险 | 岗位、简历、报告样例 |
| P1 | 数字人面试官 | 增强演示效果 | TTS、头像 |
| P1 | 学习路径推荐 | 根据能力缺口给出更细的课程或训练建议 | 求职者反馈 |
| P1 | 能力护照雏形 | 沉淀学生历次试炼和成长记录 | AI 面试证据链报告、反馈中心 |
| P1 | 面试复盘教练 | 面向求职者解释回答问题、表达短板和下一步训练任务 | AI 面试证据链报告、求职者反馈 |
| P1 | 招聘官 Copilot | 面向 HR 总结候选人亮点、风险、追问建议和真人面试决策依据 | HR 工作台、证据链报告 |
| P1 | 同岗候选人对比 | 支持 HR 对同一岗位候选人做横向能力对比和风险对比 | 人岗匹配、证据链报告、HR 工作台 |
| P1 | 校招批量初筛 | 支持同一岗位批量导入、批量匹配、排序和分组处理 | 简历解析、人岗匹配、HR 工作台 |
| P2 | 完整虚拟面试官 | 更接近真实虚拟面试 | 数字人、TTS、状态管理 |
| P2 | 试岗模拟器 | 把岗位任务试炼升级为场景化、多步骤的虚拟试岗流程 | 岗位任务试炼、任务评分标准 |
| P2 | 实时追问 | 体验更强 | 实时链路 |
| P2 | 完整视频回放 | 复查能力更强 | 对象存储、权限、成本控制 |
| P2 | 反作弊风险提示 | 基于基础事件记录做轻量风险提示，不做自动淘汰或强判定 | 面试事件记录、回答文本、任务提交记录 |
| P2 | 高级反作弊 | 更复杂可信检测，仅作为后续可信评估扩展 | 视频分析、合规策略 |
| P2 | 企业人才库 | 长期商业化能力，不进入 MVP 主实现 | 候选人报告、企业权限 |
| P2 | 企业人才雷达 | 基于企业人才库展示候选人能力分布、岗位缺口和校招人才结构 | 企业人才库、批量初筛数据 |
| P2 | AI 内推网络 | 基于能力画像、岗位画像和关系网络推荐潜在内推路径 | 能力护照、人才库、关系网络 |
| P2 | 企业 ATS 对接 | 商业化能力 | 外部接口 |

## 3. P0 功能规格与验收标准

本节是 P0 功能的产品规格沉淀。若某功能选择平衡级别，则平衡级默认覆盖 MVP 级别；未列出平衡级的功能，当前只按 MVP 级别实施和验收。

### 3.1 登录和基础角色权限

功能名称：登录和基础角色权限

功能目标：建立求职者、HR 两类用户入口，保护简历、报告、回答文字稿等敏感数据，并支持比赛演示账号快速进入系统。

功能要求：

- MVP 级别：
  - 支持注册、登录、退出登录。
  - 注册页直接选择“求职者”或“HR”角色，不建立业务管理员角色。
  - 使用用户名或邮箱 + 密码登录，不接入短信、邮箱验证码。
  - 固定提供求职者、HR 演示账号各 1 个。
  - 支持企业信息，一个企业可关联多个 HR；P0 阶段 HR 仅能访问自己创建岗位及其关联数据，不共享同企业其他 HR 的岗位数据。
  - 求职者只能访问自己的简历、画像、面试回答、任务提交和反馈。
  - 登录凭证过期后需要重新登录，不提供无感自动续期。
  - 退出登录后当前登录状态立即失效。
  - 后端校验接口权限，不能只依赖前端隐藏页面。

验收标准：

- MVP 级别：
  - 求职者和 HR 均可在注册页选择对应角色完成注册。
  - 用户可使用用户名或邮箱 + 密码成功登录，无需验证码。
  - 2 类角色均可成功登录并进入各自首页。
  - 未登录访问受保护页面时，100% 跳转登录页或返回未授权状态。
  - 求职者无法访问 HR 工作台接口。
  - 求职者无法读取其他求职者的简历、回答、任务提交或反馈。
  - HR 无法读取或修改其他 HR 创建岗位及其关联的候选人数据，即使双方属于同一企业。
  - 同一企业可成功关联至少 2 个 HR 账号。
  - 固定的求职者、HR 演示账号各 1 个，均可稳定登录。
  - 登录凭证过期后访问受保护页面返回未授权状态，并要求重新登录。
  - 退出登录后再次访问受保护页面必须重新登录。

### 3.2 简历上传与解析

功能名称：简历上传与解析

功能目标：把求职者简历转成结构化数据，为职业画像、人岗匹配、面试题生成提供可靠输入。

功能要求：

- 当前选择：采用 MVP 基线，并加入平衡级的“增强错误处理、多版本简历、同步请求状态追踪”能力；未选择 OCR、完整修订审计和恶意文件扫描。

- MVP 级别：
  - 支持可直接提取文本的 PDF 和 DOCX，不支持扫描版 PDF、图片简历和旧版 DOC。
  - 单个文件不超过 10MB，同时校验扩展名、MIME 类型和文件大小。
  - 提取姓名、联系方式、教育经历、项目经历、实习经历、技能、证书等核心字段。
  - 后端先在本地提取文本，再由模型输出结构化 JSON，并通过后端 Schema 校验。
  - 字段允许为空，AI 不得补写简历原文不存在的信息。
  - 只保存文件名、抽取文本、结构化结果、解析状态和必要错误信息。
  - 原文件只临时保存，无论解析成功或失败，任务结束后均删除。
  - 解析失败时给出可解释错误，并允许重新上传或粘贴文本继续流程。

- 平衡级别：
  - 覆盖 MVP 级别全部要求。
  - 支持部分解析成功，并显示具体字段的错误或缺失状态。
  - 求职者可人工修正结构化解析结果，并基于修正后的结果重新触发后续生成。
  - 上传新简历时保留历史版本，不覆盖旧版本；用户可指定当前使用版本。
  - 职业画像、人岗匹配、面试题和报告必须关联实际使用的简历版本。
  - 解析当前采用同步请求，页面显示加载状态；API 和数据库预留 `pending`、`running`、`completed`、`failed`、`fallback` 状态。
  - 对固定测试样本记录解析耗时；若实际测试经常超过 15 秒或出现请求超时，再升级为后台任务加前端轮询。
  - 失败任务可重试，重试沿用原简历版本，不重复创建版本记录。

验收标准：

- MVP 级别：
  - 对 10 份预置脱敏简历，至少 8 份能成功解析出核心字段。
  - 文本型 PDF 和 DOCX 可正常上传；扫描版 PDF、图片简历、旧版 DOC、类型不匹配文件和超过 10MB 的文件均被拒绝并显示具体原因。
  - 每份成功解析的简历至少保存文件名、抽取文本、结构化结果和解析状态。
  - 结构化结果符合后端 Schema，原文没有的信息保持为空，不因模型输出产生虚构字段。
  - 解析任务结束后，服务端不再保留上传的原始文件。
  - 解析结果能被职业画像和匹配流程调用。
  - 解析失败不会阻断页面，需显示失败原因和重试入口。

- 平衡级别：
  - 覆盖 MVP 级别全部验收标准。
  - 部分字段解析失败时，已成功字段仍可展示和保存，失败字段有明确状态。
  - 用户修正字段后刷新页面，修正结果仍然存在，并可被后续画像和匹配流程读取。
  - 同一求职者连续上传至少 2 份简历后，历史版本均可读取，且只能有 1 份被标记为当前使用版本。
  - 画像、匹配和报告能追溯到其使用的具体简历版本。
  - 同步解析期间页面显示加载状态；成功、失败和预置兜底分别落入 `completed`、`failed`、`fallback` 状态。
  - 对固定测试样本记录解析耗时；若多次超过 15 秒或出现请求超时，则触发升级为后台任务加轮询的技术决策。
  - 模拟解析失败后可成功重试，且重试前后使用同一个简历版本 ID。

### 3.3 岗位发布与 JD 解析

功能名称：岗位发布与 JD 解析

功能目标：帮助 HR 发布岗位，并把自然语言 JD 转成岗位画像，为匹配、面试题和岗位任务生成提供标准化依据。

功能要求：

- 当前选择：采用纯 MVP 岗位发布与 JD 解析方案。岗位只按创建者隔离，不增加企业归属字段或画像修订号，不保留岗位画像历史版本，不记录字段级来源，不建设企业组织管理页面。

- MVP 级别：
  - HR 可在一个表单内创建岗位，至少填写岗位名称、JD 原文、工作地点和岗位类型。
  - 系统保存 JD 原文，并由 AI 解析出岗位职责、必备技能、加分技能、经验要求、学历要求和风险提示。
  - 必备技能与加分技能分别保存为两个列表；P0 不为每项技能增加重要度、原文证据或字段来源。
  - AI 输出通过后端 Schema 校验后进入待确认状态，不能未经 HR 确认直接用于后续业务流程。
  - HR 可以修改 AI 解析结果；点击确认后，当前岗位画像才能被人岗匹配、面试题生成和岗位任务生成读取。
  - JD 解析失败时，HR 可以重试、跳过 AI 后人工填写岗位画像，或在演示场景中显式使用预置岗位画像继续流程。
  - 预置岗位画像必须标记为演示兜底，不能展示为当前 JD 的真实 AI 解析结果。
  - HR 只能查看和管理自己创建的岗位。
  - 经验要求和学历要求允许参与人岗匹配，采用中等权重，但不作为自动淘汰或硬性拒绝条件。
  - 岗位状态包含草稿、解析中、待确认、已确认、已发布、已关闭、已归档和解析失败。
  - 基础状态流转为“草稿 -> 解析中 -> 待确认 -> 已确认 -> 已发布”；解析失败进入失败状态；已发布岗位可关闭，关闭后可归档。
  - HR 可以修改已确认或已发布岗位。修改 JD 或岗位画像后必须重新确认，未经再次确认不得用于新的匹配、面试题或岗位任务生成。
  - P0 只保留当前确认画像和最近一次 AI 原始输出；重新解析、修改或再次确认会覆盖当前结果，不保存画像修订号。
  - 岗位被修改时，系统将已有匹配结果、面试题和岗位任务标记为过期；岗位画像再次确认后提示重新生成。
  - P0 不记录“AI 提取、HR 输入、HR 修改”等字段级来源，不建设完整字段修订审计。

验收标准：

- MVP 级别：
  - HR 能在 1 个表单内完成岗位创建。
  - 至少 5 条预置 JD 可成功解析出符合后端 Schema 的岗位画像。
  - 每份成功解析的岗位画像均包含岗位职责、必备技能、加分技能、经验要求、学历要求和风险提示字段；原文未提供的信息允许为空，AI 不得自行补写事实。
  - AI 解析完成后，岗位停留在待确认状态；未经 HR 确认，人岗匹配、面试题生成和岗位任务生成均不能读取该画像。
  - HR 修改并确认岗位画像后，后续模块读取到的是确认后的当前结果。
  - 模拟 AI 解析失败时，可以通过重试、人工填写或显式预置兜底中的任一方式继续流程，并能区分真实解析结果与预置结果。
  - 一个 HR 无法读取或修改另一个 HR 创建的岗位，即使两个账号属于同一企业。
  - 经验和学历可以进入匹配计算，但不会单独触发候选人淘汰或拒绝。
  - 岗位可以完整流转经过草稿、解析中、待确认、已确认、已发布、已关闭和已归档状态，解析失败时进入失败状态。
  - 已确认或已发布岗位被修改后会重新进入待确认状态，再次确认前不能触发新的下游生成。
  - 岗位修改后，旧匹配结果、旧面试题和旧岗位任务被标记为过期，并提供重新生成入口。
  - 多次重新解析、修改和确认后，系统只保留当前岗位画像和最近一次 AI 原始输出，不产生历史画像列表或修订号。

### 3.4 职业画像

功能名称：职业画像

功能目标：基于简历解析结果生成求职者能力画像，让学生理解自身能力，也让后续匹配和面试生成有统一输入。

功能要求：

- MVP 级别：
  - 生成技能标签、岗位倾向、优势、发展方向 / 待验证项和项目亮点。
  - 每项技能标签、优势、发展方向 / 待验证项和项目亮点至少绑定一条简历字段及证据文本。
  - 技能标签使用 AI 输出的自由字符串，由后端负责去重，并默认限制为 5-12 个、单个标签不超过 50 个字符；P0 不建立标准标签字典。
  - 输出版本化结构化 JSON，并经过后端 JSON Schema 校验后保存和供后续模块调用。
  - 支持可视化卡片展示。
  - 求职者只能查看自己的职业画像；HR 只能查看已申请其本人创建岗位的候选人画像。
  - 每次成功生成职业画像时新增画像版本并关联具体简历版本，默认读取最新成功版本；P0 不提供版本比较、指定版本切换或回滚。
  - 首次生成失败后最多自动重试 1 次，仍失败时显示原因并允许人工重试；演示场景可显式使用带兜底标记的预置画像。
  - 画像只能基于简历证据，不得推断性别、年龄、民族、婚育、宗教、健康、残障等敏感属性，也不得输出无证据的人格、心理、诚信或潜力判断。

验收标准：

- MVP 级别：
  - 每份成功解析的简历都能生成至少 1 份职业画像。
  - 每份画像至少包含 5 个技能标签、2 个优势、2 个发展方向 / 待验证项和 1 个岗位倾向。
  - 职业画像 JSON 通过后端 Schema 校验；字段缺失、类型错误、数量超限或包含禁止字段的输出不得入库。
  - 技能标签、优势、发展方向 / 待验证项和项目亮点的证据覆盖率为 100%，每项至少包含 `source_field` 和 `evidence_text`。
  - 简历原文没有的信息保持未知或标记为待验证，画像中不出现敏感属性推断和无证据的人格、心理、诚信或潜力结论。
  - 求职者无法读取其他求职者画像；HR 无法读取未申请其本人创建岗位的候选人画像。
  - 同一求职者基于新简历或重新生成画像后产生新的画像版本，旧版本不被覆盖，默认读取最新成功版本。
  - 画像结果可被匹配模块读取，匹配结果能够追溯到使用的职业画像版本和简历版本。
  - 模拟首次 AI 生成失败时系统最多自动重试 1 次；再次失败后可人工重试，使用预置画像时页面和数据均明确标记为演示兜底。

### 3.5 人岗匹配

功能名称：人岗匹配

功能目标：计算候选人与岗位的匹配度，帮助 HR 快速筛选，并解释匹配理由、能力缺口和风险点。

功能要求：

- MVP 级别：
  - 求职者主动点击“申请岗位”后创建 `application` 关系；P0 不支持 HR 邀请候选人。
  - 输入已确认的职业画像、岗位画像、求职意向和对应申请关系。
  - 固定使用技能匹配、经历匹配、项目相关度和求职意向 4 个评分维度。
  - 固定权重为技能匹配 30%、经历匹配 25%、项目相关度 35%、求职意向 10%。
  - 每个维度先归一化为 0-100 分，再按固定权重计算 0-100 总匹配分。
  - 学历、学校和毕业年份仅在 JD 明确提出对应要求时，作为经历匹配维度的子项参与评分；系统不得自行推断学校偏好。
  - 缺少必备技能或未满足 JD 明确要求时只扣分并形成缺口提示，不自动淘汰或拒绝候选人。
  - LLM 只负责从简历和 JD 提取标准化标签，并根据后端评分结果生成推荐理由、能力缺口和风险解释；不得修改分数、权重或排序。
  - 输出四个维度分、总匹配分、推荐理由、能力缺口和风险点。
  - 支持 HR 查看候选人排序。
  - 匹配规则固定为 `match_rule_v1`，每条结果保存规则版本和四个维度分。
  - 学历、学校和毕业年份允许按上述规则参与评分；性别、年龄、出生日期、民族、婚育、宗教、健康、残障、照片和外貌等属性完全排除。
  - P0 使用 SQLite 保存申请关系和匹配结果，不引入向量数据库、机器学习排序模型或独立推荐服务。

- 平衡级别：
  - 覆盖 MVP 级别全部要求。
  - 支持求职者主动申请和 HR 邀请两种候选来源。
  - 可增加语义相似度辅助、岗位级权重配置、规则快照和更完整的证据引用。
  - 准备 30-50 个脱敏人工标注样例，比较系统排序与人工排序的一致率。
  - 仍由规则负责评分，LLM 只负责标签提取和结果解释，最终决策由 HR 作出。

验收标准：

- MVP 级别：
  - 每个候选人对每个岗位生成 0-100 匹配分。
  - 每条结果包含技能、经历、项目和求职意向 4 个 0-100 维度分，按 30% / 25% / 35% / 10% 权重计算的总分可复算且结果一致。
  - 每条匹配结果至少包含 3 条推荐理由和 2 条风险或缺口。
  - HR 工作台能按匹配分降序展示候选人。
  - 缺少必备技能的候选人仍保留在排序中，结果标记对应缺口，不产生自动淘汰状态。
  - 每条匹配结果记录 `match_rule_v1`，刷新或重新查询后规则版本和分数保持一致。
  - 性别、年龄、出生日期、民族、婚育、宗教、健康、残障、照片和外貌等属性不会出现在评分输入、理由或风险点中。
  - 使用首批 2 类岗位和 10-20 个脱敏人工标注样例完成排序人工检查。

### 3.6 面试题生成

功能名称：面试题生成

功能目标：根据简历、岗位和匹配结果生成个性化面试题，避免泛化题库，让问题服务于能力验证。

功能要求：

- 当前选择：采用 MVP 基线，并加入平衡级的 HR 精细调整、题目数量调整、草稿保存、确认版本回退和修改记录能力；不选择题目难度分层、历史题目模板缓存、模型二次内容审核和企业级审计系统。
- MVP + 已选平衡能力：
  - 仅当岗位画像已确认、候选人已申请该岗位且匹配结果有效时生成面试题。
  - 默认生成 5 道题，HR 可在 5-8 道范围内调整本次生成数量。
  - 题目固定覆盖项目经历、岗位技能和能力缺口 3 类，不要求难度分层。
  - 每道题保存题目正文、题目类别、考察能力、提问依据、来源类型和简短来源引用。
  - 来源类型只允许简历字段、岗位要求和匹配缺口。
  - HR 可选择、删除、手动编辑或单题重新生成题目，调整结果自动保存为当前草稿，并在调整后确认整套题目。
  - 只有已确认的题目集才能进入候选人面试会话。
  - 后端使用确定性规则拦截敏感或歧视性题目；P0 不增加第二次模型审核。
  - 每个申请关系保留一份当前可编辑草稿；每次确认整套题目时基于草稿创建不可变的已确认版本。
  - 支持从已确认版本继续创建新草稿，并支持将历史确认版本恢复为当前版本；回退不覆盖或删除已有确认版本。
  - 保存当前草稿、历次确认版本、题目来源、当前生效版本和修改记录。
  - 题目选择、删除、手动编辑、单题重新生成、整套确认和版本回退均记录操作者、操作时间、动作类型和变更前后摘要。
  - 面试题生成先采用同步请求，前端显示加载状态；API 和数据库预留 `pending`、`running`、`completed`、`failed`、`fallback` 状态。
  - 实际测试中若生成经常超过 15 秒或出现请求超时，再升级为后台任务加前端轮询，P0 不提前引入消息队列。
  - 生成失败时可重试或显式使用对应岗位类别的预置题目，预置结果必须标记为 `fallback`。

验收标准：

- MVP + 已选平衡能力：
  - 默认可生成 5 道题，HR 选择 6、7 或 8 道时，后端按所选数量返回；小于 5 或大于 8 的请求被拒绝。
  - 每套题覆盖项目经历、岗位技能和能力缺口 3 类，且每道题包含考察能力和提问依据。
  - 默认 5 道题时至少 4 道具有有效来源；生成 6-8 道时，至少 80% 的题目能关联到简历字段、岗位要求或匹配缺口。
  - 固定脱敏样本由产品 / HR 人工检查题目与来源引用是否真实相关，不以模型自评替代验收。
  - 包含敏感属性或歧视性内容的题目会被后端规则拦截，不能进入 HR 确认列表。
  - HR 可以完成题目选择、删除、手动编辑、单题重新生成和整套确认。
  - 编辑页面刷新或重新登录后仍可恢复当前未确认草稿；未确认题目不能被候选人面试会话读取。
  - 确认后刷新页面仍能读取当前生效版本，已确认版本内容不会因后续草稿编辑而改变。
  - 至少产生 2 个已确认版本后，HR 可以恢复上一确认版本，恢复后候选人读取到的是恢复后的当前版本。
  - 选择、删除、编辑、单题重新生成、确认和回退后均能查询对应修改记录，记录包含操作者、时间、动作类型和变更前后摘要。
  - 删除草稿或回退版本不会删除已有确认版本和历史修改记录。
  - 同步生成期间页面显示加载状态；成功、失败和预置兜底分别落入 `completed`、`failed`、`fallback` 状态。
  - 模拟真实生成失败时，可以重试或使用明确标记的预置题目继续流程。
  - 对固定测试样本记录生成耗时；若多次超过 15 秒或出现请求超时，则触发升级为后台任务加轮询的技术决策。

### 3.7 岗位任务试炼

功能名称：岗位任务试炼

功能目标：用一个轻量岗位任务验证候选人的真实岗位能力，形成区别于普通简历筛选工具的核心差异点。

功能要求：

- MVP 级别：
  - 根据岗位画像生成 1 个轻量任务。
  - 任务包含背景、要求、交付物、评分标准。
  - 候选人可提交文本结果或链接。
  - 任务结果进入 AI 面试证据链报告。

验收标准：

- MVP 级别：
  - 每个岗位至少能生成 1 个任务。
  - 任务说明包含不少于 3 项评分标准。
  - 候选人提交后，系统记录提交内容、提交时间、状态。
  - 报告中能引用任务表现作为证据。

### 3.8 轻量面试回答记录

功能名称：轻量面试回答记录

功能目标：保留面试回答闭环，让候选人按题目回答，同时避免一开始做复杂数字人和完整视频系统。

功能要求：

- MVP 级别：
  - 候选人逐题查看面试题并回答。
  - 请求摄像头和麦克风权限。
  - 记录面试开始、结束、提交等基础事件。
  - 默认不长期保存完整视频。

验收标准：

- MVP 级别：
  - 候选人可完成至少 5 道题的回答流程。
  - 系统记录 sessionId、questionId、startTime、endTime、submitTime。
  - 摄像头或麦克风拒绝授权时，页面给出可解释提示。

### 3.9 答后 ASR 转写

功能名称：答后 ASR 转写

功能目标：把候选人回答转成 HR 和 AI 可读文本，为报告评价和证据引用提供输入。

功能要求：

- MVP 级别：
  - 使用浏览器 Web Speech API 或可替代文字稿流程。
  - 每道题生成回答文字稿。
  - ASR 失败时允许手动输入或使用备用文字稿。

验收标准：

- MVP 级别：
  - Chrome / Edge 下能完成转写或手动文字稿提交。
  - 每道题至少保存一份文字稿记录。
  - ASR 不可用时，流程仍能继续生成报告。

### 3.10 AI 面试证据链报告

功能名称：AI 面试证据链报告

功能目标：输出 HR 可读的结构化决策报告，把评分、回答证据、任务证据、匹配依据和成长建议串起来。

功能要求：

- MVP 级别：
  - 生成 HR 版报告。
  - 包含总评分、维度评分、推荐结论、风险点、回答证据、任务证据、成长建议。
  - 每个重要结论尽量绑定证据来源。
  - AI 输出使用结构化格式约束。
- 平衡级别：
  - 覆盖 MVP 级别全部要求。
  - 区分 HR 版和求职者版报告。
  - 支持展开证据片段。
  - 记录 AI 模型、提示词版本、生成时间和输入摘要。

验收标准：

- MVP 级别：
  - 每个完成面试和任务提交的候选人可生成 1 份报告。
  - 报告至少包含 4 个评分维度、3 条证据、2 条风险点、3 条建议。
  - 报告可被 HR 工作台打开查看。

### 3.11 HR 工作台

功能名称：HR 工作台

功能目标：给 HR 提供筛选和决策入口，在一个工作台完成岗位查看、候选人排序、报告查看和真人面试决策。

功能要求：

- MVP 级别：
  - 展示 HR 发布的岗位列表。
  - 展示候选人匹配排序。
  - 可查看候选人报告。
  - 可标记是否进入真人面试。
- 平衡级别：
  - 覆盖 MVP 级别全部要求。
  - 支持筛选、搜索、状态过滤。
  - 支持候选人备注。
  - 支持简单统计，例如候选人数、平均匹配分、推荐进入面试人数。

验收标准：

- MVP 级别：
  - HR 能在一个页面完成候选人排序、报告查看和决策标记。
  - 每个候选人卡片至少展示姓名、岗位、匹配分、状态、报告入口。
  - 决策状态可保存，刷新后仍存在。
- 平衡级别：
  - 覆盖 MVP 级别全部验收标准。
  - 支持按状态和岗位筛选候选人。
  - HR 备注可保存、编辑、删除。
  - 工作台统计数据与候选人列表数量一致。

### 3.12 求职者报告 / 反馈中心

功能名称：求职者报告 / 反馈中心

功能目标：让求职者看到自己的画像、面试表现、能力短板和下一步改进建议，形成成长闭环。

功能要求：

- MVP 级别：
  - 求职者可查看职业画像。
  - 可查看面试反馈和成长建议。
  - 展示适配岗位、优势、短板、改进方向。

验收标准：

- MVP 级别：
  - 每个完成报告的求职者可查看 1 份反馈。
  - 反馈至少包含 2 条优势、2 条短板、3 条改进建议。
  - 求职者不能查看 HR 内部风险备注或决策备注。

### 3.13 多 Agent 协作展示

功能名称：多 Agent 协作展示

功能目标：在答辩和演示中清楚解释系统内部如何分工：解析、画像、匹配、面试、任务、报告各自由不同 Agent 或步骤负责。

功能要求：

- MVP 级别：
  - 展示固定工作流节点。
  - 每个节点显示输入、输出、状态。
  - Agent 仅作为职责清晰的流程展示，不做自由决策。

验收标准：

- MVP 级别：
  - 至少展示 6 个节点：简历解析、职业画像、JD 解析、人岗匹配、面试题生成、报告生成。
  - 每个节点有 completed、failed、fallback 状态。
  - 演示数据可完整跑出一条 Agent 流程。

### 3.14 演示预置数据

功能名称：演示预置数据

功能目标：在 AI、ASR、网络或现场环境不稳定时，用预置岗位、简历、画像、匹配结果和报告保证演示不断链。

功能要求：

- MVP 级别：
  - 准备至少 1-2 类岗位的完整预置数据。
  - 包含岗位、简历、画像、匹配结果、面试题、任务、文字稿、报告。
  - AI 失败时允许切换到预置结果。

验收标准：

- MVP 级别：
  - 至少 2 个岗位、3 份候选人简历、3 份完整报告可用于演示。
  - 断网或 AI 失败情况下，HR 工作台和报告页仍可展示。
  - 预置数据能跑通 roadmap 演示顺序的关键页面。

## 4. 推荐实施顺序

1. 登录和基础角色权限。
2. 简历上传与解析。
3. 岗位发布与 JD 解析。
4. 职业画像。
5. 人岗匹配。
6. 面试题生成。
7. 岗位任务试炼。
8. 轻量面试回答记录。
9. 答后 ASR 转写或可替代文字稿流程。
10. AI 面试证据链报告。
11. HR 工作台。
12. 求职者反馈。
13. 多 Agent 协作展示。
14. 演示预置数据和失败兜底。
15. 再补数字人、学习路径、能力护照和面试复盘教练。
16. 在 HR 工作台稳定后，再做招聘官 Copilot、同岗候选人对比和校招批量初筛。
17. 最后规划试岗模拟器、反作弊风险提示、企业人才雷达和 AI 内推网络，用于高级版和商业化展示。

## 5. 3-4 周个人开发里程碑

| 时间 | 目标 | 产出 |
|---|---|---|
| 第 1 周 | 用户、简历、岗位基础闭环 | 可登录、可上传简历、可发布岗位 |
| 第 2 周 | AI 解析、画像、匹配、面试题 | 能生成画像、岗位画像、匹配结果和面试题 |
| 第 3 周 | 岗位任务试炼、面试回答、证据链报告、HR 工作台 | 能完成试炼、能回答、能生成证据化报告、HR 能决策 |
| 第 4 周 | 演示稳定性、预置数据、Agent 展示、移动端适配、部署 | 固定公开链接、备用数据、核心页面桌面和手机可用 |

## 6. 演示顺序

1. HR 注册并发布岗位。
2. 系统解析 JD 并生成岗位画像。
3. 求职者上传简历。
4. 系统生成候选人画像和匹配分。
5. HR 查看排序与推荐理由。
6. 系统生成个性化面试题。
7. 系统生成岗位任务试炼，用一个小任务验证候选人真实能力。
8. 候选人进入轻量面试，打开摄像头逐题回答，并提交岗位任务结果。
9. 系统在回答结束后转写文字稿，或使用可替代文字稿流程继续演示。
10. 系统给出 AI 面试证据链报告和成长反馈。
11. HR 最终点击是否进入真人面试。

## 7. 演示兜底策略

- 主路径使用真实上传、真实解析、真实生成。
- 备用路径使用预置岗位、简历、候选人画像、匹配结果和报告。
- AI 失败时展示可解释错误，允许切换到预置结果继续演示。
- ASR 失败时允许展示备用文字稿或手动输入文字稿。
- 岗位任务试炼生成失败时允许切换到预置试炼任务，但任务结果和 AI 面试证据链报告仍要能进入主流程。
- 网络不稳定时优先保证 HR 工作台和报告页可展示。

## 8. 可以先模拟或简化的部分

- 高拟真数字人。
- 完整虚拟面试官。
- 完整视频回放。

## 11. MVP 与平衡级升级边界

| 决策项 | MVP 选择 | 平衡级选择 | 升级条件 |
|---|---|---|---|
| 架构 | FastAPI 模块化单体 | FastAPI + 后台任务队列 | AI 任务耗时明显影响体验 |
| 数据库 | SQLite 起步 | PostgreSQL | 进入真实多用户试用 |
| Agent | 手写固定工作流 | LangGraph 或状态机 | Agent 步骤和异常分支增多 |
| 面试与试炼 | 题目 + 岗位任务 + 摄像头回答 + 答后转写 | 虚拟面试官 + 动态追问 + 短期音视频保存 | 需要更强演示沉浸感 |
| 文件 | 少存文件，默认不长期存视频 | 对象存储 + 签名 URL | 需要音频/视频复查 |
| 模型 | 低成本稳定模型 | 多模型适配和备用模型 | 主模型不稳定或效果不足 |
| 部署 | 固定 HTTPS 演示链接 | 更完整监控和告警 | 真实用户增长 |
