# HireLink 路线图

## 1. 总体原则

- 优先跑通主闭环。
- 比赛版主线围绕“能力验证”展开，不做功能堆叠型招聘系统。
- P0 必须体现“简历解析 -> 岗位理解 -> 人岗匹配 -> 个性化面试 -> 岗位能力试炼 -> AI 面试证据链报告 -> 求职者成长中心”的完整逻辑。
- P0 先保证能演示、能讲清楚、能稳定复现。
- 演示数据通过预置数据和受控重置流程维护，不扩展独立维护页面。
- 可信面试不作为当前优先实现功能；MVP 只保留基础业务事件，不做可见风险判断和强判定。
- P1 再提升体验和可信度。
- P2 才做增强型能力。
- 个人 3-4 周开发周期内，优先选择低风险、可回滚、可替换的实现。
- 第一版优先覆盖 1-2 类岗位，并使用脱敏真实数据做演示。

## 2. 开发优先级

| 优先级 | 模块 | 原因 | 依赖 |
|---|---|---|---|
| P0 | 登录和基础角色权限 | 所有功能的入口，也保护敏感数据；保留演示账号 | 无 |
| P0 | 简历上传与解析 | 后续画像和匹配的输入源 | 用户系统 |
| P0 | 岗位发布与 JD 解析 | 匹配和智能提问的输入源 | 用户系统 |
| P0 | 职业画像 | 连接简历与后续 AI 流程 | 简历解析 |
| P0 | 人岗匹配 | HR 最核心的筛选能力 | 职业画像、岗位画像 |
| P0 / P2 | 智能面试提问 | P0 生成可追溯的个性化题目，P2 在同一功能内扩展动态追问 | 简历、岗位、匹配结果、未来实时回答 |
| P0 / P2 | 岗位能力试炼 | P0 用单个轻量任务验证真实能力，P2 在同一功能内扩展场景化多步骤模拟 | 岗位画像、匹配结果、任务评分标准 |
| P0 / P2 | 面试会话与记录 | P0 管理设备降级、会话、回答、实时转写和确认，P2 扩展授权音视频回放 | 智能面试提问、浏览器权限、对象存储 |
| P0 | AI 面试证据链报告 | 最终价值输出，需要包含评分、回答证据、任务表现证据和成长建议 | 回答文本、岗位能力试炼结果、画像、岗位信息 |
| P0 / P1 | 智能招聘工作台 | P0 提供岗位、排序、报告和人工决策，P1 扩展 Copilot、同岗对比和批量初筛 | 匹配、报告、批量候选人 |
| P0 / P1 | 求职者成长中心 | P0 提供脱敏报告和行动建议，P1 扩展学习路径、回答复盘与训练任务 | AI 面试证据链报告 |
| P0 | 多 Agent 协作面板 | 基于真实 `ai_runs` 说明固定 Orchestrator 内部如何分工协作 | 解析、匹配、面试、任务、报告流程 |
| P0 | 演示预置数据 | 降低比赛现场失败风险 | 岗位、简历、报告样例 |
| P1 / P2 | 虚拟面试官 | P1 提供头像、语音和基础动画，P2 扩展沉浸式形象、状态联动与实时交互 | TTS、头像、会话状态 |
| P1 | 能力护照雏形 | 沉淀学生历次试炼和成长记录 | AI 面试证据链报告、求职者成长中心 |
| P1 | 真人面试预约 | 承接 HR 的“进入真人面试”决定，由 HR 发送绑定申请预约链接，候选人选择指定主面试官可用时间，形成企业正式线上／线下面试基础预约闭环 | 完整上游评估结果、岗位创建 HR 授权、指定主面试官、基础档期、站内通知、会议或地点、预约状态与审计 |
| P2 | 可信面试 | 在合规审查和人工复核前提下，基于必要过程数据提供可解释风险提示与高级可信评估，不自动淘汰 | 面试事件、回答文本、任务提交、合规策略 |
| P2 | 企业人才运营 | 沉淀授权候选人资产，并提供检索、岗位关联、能力分布和人才洞察 | 候选人报告、企业权限、批量初筛数据 |
| P2 | AI 内推网络 | 核心差异化能力；基于能力画像、岗位画像和经授权关系网络识别潜在岗位连接与内推路径 | 能力护照、企业人才运营、授权关系网络 |
| P2 | 企业 ATS 对接 | 商业化能力 | 外部接口 |

### 2.1 核心差异化能力定位

- 岗位能力试炼、AI 面试证据链报告、人岗匹配和多 Agent 协作面板构成当前比赛版的核心差异化能力。
- AI 内推网络作为第五项核心差异化能力进入长期产品叙事，保持 P2 规划状态，不进入当前 MVP、3-4 周里程碑或演示主流程。
- AI 内推网络负责关系连接与内推路径推荐；企业人才运营负责企业内部人才资产与聚合洞察，两者不共用一级入口。

## 3. P0 功能规格与验收标准

本节是 P0 功能的产品规格沉淀。若某功能选择平衡级别，则平衡级默认覆盖 MVP 级别；未列出平衡级的功能，当前只按 MVP 级别实施和验收。

### 3.1 登录和基础角色权限

功能名称：登录和基础角色权限

功能目标：建立求职者、HR 两类用户入口，保护简历、报告、回答文字稿等敏感数据，并支持比赛演示账号快速进入系统。

功能要求：

- MVP 级别：
  - 支持注册、登录、退出登录。
  - 注册页直接选择“求职者”或“HR”角色，不建立业务管理员角色。
  - 使用用户名或邮箱 + 密码登录，不接入短信、邮箱验证码。
  - 固定提供求职者、HR 演示账号各 1 个。
  - 支持企业信息，一个企业可关联多个 HR；P0 阶段 HR 仅能访问自己创建岗位及其关联数据，不共享同企业其他 HR 的岗位数据。
  - 求职者只能访问自己的简历、画像、面试回答、任务提交和反馈。
  - 登录凭证过期后需要重新登录，不提供无感自动续期。
  - 退出登录后当前登录状态立即失效。
  - 后端校验接口权限，不能只依赖前端隐藏页面。

验收标准：

- MVP 级别：
  - 求职者和 HR 均可在注册页选择对应角色完成注册。
  - 用户可使用用户名或邮箱 + 密码成功登录，无需验证码。
  - 2 类角色均可成功登录并进入各自首页。
  - 未登录访问受保护页面时，100% 跳转登录页或返回未授权状态。
  - 求职者无法访问智能招聘工作台接口。
  - 求职者无法读取其他求职者的简历、回答、任务提交或反馈。
  - HR 无法读取或修改其他 HR 创建岗位及其关联的候选人数据，即使双方属于同一企业。
  - 同一企业可成功关联至少 2 个 HR 账号。
  - 固定的求职者、HR 演示账号各 1 个，均可稳定登录。
  - 登录凭证过期后访问受保护页面返回未授权状态，并要求重新登录。
  - 退出登录后再次访问受保护页面必须重新登录。

### 3.2 简历上传与解析

功能名称：简历上传与解析

功能目标：把求职者简历转成结构化数据，为职业画像、人岗匹配和智能提问提供可靠输入。

功能要求：

- 当前选择：采用 MVP 基线，并加入平衡级的“增强错误处理、多版本简历、同步请求状态追踪”能力；未选择 OCR、完整修订审计和恶意文件扫描。

- MVP 级别：
  - 支持可直接提取文本的 PDF 和 DOCX，不支持扫描版 PDF、图片简历和旧版 DOC。
  - 单个文件不超过 10MB，同时校验扩展名、MIME 类型和文件大小。
  - 提取姓名、联系方式、教育经历、项目经历、实习经历、技能、证书等核心字段。
  - 后端先在本地提取文本，再由模型输出结构化 JSON，并通过后端 Schema 校验。
  - 字段允许为空，AI 不得补写简历原文不存在的信息。
  - 始终保存文件名、抽取文本、结构化结果、解析状态和必要错误信息。
  - 上传时允许求职者选择是否保存原文件，默认不保存。
  - 未选择保存时，原文件无论解析成功或失败都在任务结束后删除；选择保存时，原文件转入受控持久目录并只能通过鉴权接口访问。
  - 已保存的原文件只能由简历所有者，以及该求职者已申请岗位的创建 HR 查看；同企业其他 HR、其他求职者和未建立对应申请关系的 HR 不具备访问权限。
  - 解析失败时给出可解释错误，并允许重新上传或粘贴文本继续流程。

- 平衡级别：
  - 覆盖 MVP 级别全部要求。
  - 支持部分解析成功，并显示具体字段的错误或缺失状态。
  - 求职者可人工修正结构化解析结果，并基于修正后的结果重新触发后续生成。
  - 上传新简历时保留历史版本，不覆盖旧版本；用户可指定当前使用版本。
  - 职业画像、人岗匹配、面试题和报告必须关联实际使用的简历版本。
  - 解析当前采用同步请求，页面显示加载状态；API 和数据库预留 `pending`、`running`、`completed`、`failed`、`fallback` 状态。
  - 对固定测试样本记录解析耗时；若实际测试经常超过 15 秒或出现请求超时，再升级为后台任务加前端轮询。
  - 失败任务可重试，重试沿用原简历版本，不重复创建版本记录。

验收标准：

- MVP 级别：
  - 对 10 份预置脱敏简历，至少 8 份能成功解析出核心字段。
  - 文本型 PDF 和 DOCX 可正常上传；扫描版 PDF、图片简历、旧版 DOC、类型不匹配文件和超过 10MB 的文件均被拒绝并显示具体原因。
  - 每份成功解析的简历至少保存文件名、抽取文本、结构化结果和解析状态。
  - 结构化结果符合后端 Schema，原文没有的信息保持为空，不因模型输出产生虚构字段。
  - 未选择保存原文件时，解析任务结束后服务端不再保留原文件。
  - 选择保存原文件时，刷新后仍能查看保留状态；简历所有者可以读取。
  - 求职者申请某个已发布岗位后，该岗位创建 HR 可以通过鉴权接口读取该求职者选择保留的简历原文件。
  - 同企业其他 HR、其他求职者、岗位非创建者以及不存在对应申请关系的 HR 访问原文件时，后端均返回未授权或禁止访问。
  - 解析结果能被职业画像和匹配流程调用。
  - 解析失败不会阻断页面，需显示失败原因和重试入口。

- 平衡级别：
  - 覆盖 MVP 级别全部验收标准。
  - 部分字段解析失败时，已成功字段仍可展示和保存，失败字段有明确状态。
  - 用户修正字段后刷新页面，修正结果仍然存在，并可被后续画像和匹配流程读取。
  - 同一求职者连续上传至少 2 份简历后，历史版本均可读取，且只能有 1 份被标记为当前使用版本。
  - 画像、匹配和报告能追溯到其使用的具体简历版本。
  - 同步解析期间页面显示加载状态；成功、失败和预置兜底分别落入 `completed`、`failed`、`fallback` 状态。
  - 对固定测试样本记录解析耗时；若多次超过 15 秒或出现请求超时，则触发升级为后台任务加轮询的技术决策。
  - 模拟解析失败后可成功重试，且重试前后使用同一个简历版本 ID。

### 3.3 岗位发布与 JD 解析

功能名称：岗位发布与 JD 解析

功能目标：帮助 HR 发布岗位，并把自然语言 JD 转成岗位画像，为匹配、面试题和岗位任务生成提供标准化依据。

功能要求：

- 当前选择：采用纯 MVP 岗位发布与 JD 解析方案。岗位只按创建者隔离，不增加企业归属字段或画像修订号，不保留岗位画像历史版本，不记录字段级来源，不建设企业组织管理页面。

- MVP 级别：
  - HR 可在一个表单内创建岗位，至少填写岗位名称、JD 原文、工作地点和岗位类型。
  - 系统保存 JD 原文，并由 AI 解析出岗位职责、必备技能、加分技能、经验要求、学历要求和风险提示。
  - 必备技能与加分技能分别保存为两个列表；P0 不为每项技能增加重要度、原文证据或字段来源。
  - AI 输出通过后端 Schema 校验后进入待确认状态，不能未经 HR 确认直接用于后续业务流程。
  - HR 可以修改 AI 解析结果；点击确认后，当前岗位画像才能被人岗匹配、智能提问和岗位任务生成读取。
  - JD 解析失败时，HR 可以重试、跳过 AI 后人工填写岗位画像，或在演示场景中显式使用预置岗位画像继续流程。
  - 预置岗位画像必须标记为演示兜底，不能展示为当前 JD 的真实 AI 解析结果。
  - HR 只能查看和管理自己创建的岗位。
  - 经验要求和学历要求允许参与人岗匹配，采用中等权重，但不作为自动淘汰或硬性拒绝条件。
  - 岗位状态包含草稿、解析中、待确认、已确认、已发布、已关闭、已归档和解析失败。
  - 基础状态流转为“草稿 -> 解析中 -> 待确认 -> 已确认 -> 已发布”；解析失败进入失败状态；已发布岗位可关闭，关闭后可归档。
  - HR 可以修改已确认或已发布岗位。修改 JD 或岗位画像后必须重新确认，未经再次确认不得用于新的匹配、面试题或岗位任务生成。
  - P0 只保留当前确认画像和最近一次 AI 原始输出；重新解析、修改或再次确认会覆盖当前结果，不保存画像修订号。
  - 岗位被修改时，系统将已有匹配结果、面试题和岗位任务标记为过期；岗位画像再次确认后提示重新生成。
  - P0 不记录“AI 提取、HR 输入、HR 修改”等字段级来源，不建设完整字段修订审计。

验收标准：

- MVP 级别：
  - HR 能在 1 个表单内完成岗位创建。
  - 至少 5 条预置 JD 可成功解析出符合后端 Schema 的岗位画像。
  - 每份成功解析的岗位画像均包含岗位职责、必备技能、加分技能、经验要求、学历要求和风险提示字段；原文未提供的信息允许为空，AI 不得自行补写事实。
  - AI 解析完成后，岗位停留在待确认状态；未经 HR 确认，人岗匹配、智能提问和岗位任务生成均不能读取该画像。
  - HR 修改并确认岗位画像后，后续模块读取到的是确认后的当前结果。
  - 模拟 AI 解析失败时，可以通过重试、人工填写或显式预置兜底中的任一方式继续流程，并能区分真实解析结果与预置结果。
  - 一个 HR 无法读取或修改另一个 HR 创建的岗位，即使两个账号属于同一企业。
  - 经验和学历可以进入匹配计算，但不会单独触发候选人淘汰或拒绝。
  - 岗位可以完整流转经过草稿、解析中、待确认、已确认、已发布、已关闭和已归档状态，解析失败时进入失败状态。
  - 已确认或已发布岗位被修改后会重新进入待确认状态，再次确认前不能触发新的下游生成。
  - 岗位修改后，旧匹配结果、旧面试题和旧岗位任务被标记为过期，并提供重新生成入口。
  - 多次重新解析、修改和确认后，系统只保留当前岗位画像和最近一次 AI 原始输出，不产生历史画像列表或修订号。

### 3.4 职业画像

功能名称：职业画像

功能目标：基于简历解析结果生成求职者能力画像，让学生理解自身能力，也让后续匹配和面试生成有统一输入。

功能要求：

- MVP 级别：
  - 生成技能标签、岗位倾向、优势、发展方向 / 待验证项和项目亮点。
  - 每项技能标签、优势、发展方向 / 待验证项和项目亮点至少绑定一条简历字段及证据文本。
  - 技能标签使用 AI 输出的自由字符串，由后端负责去重，并默认限制为 5-12 个、单个标签不超过 50 个字符；P0 不建立标准标签字典。
  - 输出版本化结构化 JSON，并经过后端 JSON Schema 校验后保存和供后续模块调用。
  - 支持可视化卡片展示。
  - 求职者只能查看自己的职业画像；HR 只能查看已申请其本人创建岗位的候选人画像。
  - 每次成功生成职业画像时新增画像版本并关联具体简历版本，默认读取最新成功版本；P0 不提供版本比较、指定版本切换或回滚。
  - 首次生成失败后最多自动重试 1 次，仍失败时显示原因并允许人工重试；演示场景可显式使用带兜底标记的预置画像。
  - 画像只能基于简历证据，不得推断性别、年龄、民族、婚育、宗教、健康、残障等敏感属性，也不得输出无证据的人格、心理、诚信或潜力判断。

验收标准：

- MVP 级别：
  - 每份成功解析的简历都能生成至少 1 份职业画像。
  - 每份画像至少包含 5 个技能标签、2 个优势、2 个发展方向 / 待验证项和 1 个岗位倾向。
  - 职业画像 JSON 通过后端 Schema 校验；字段缺失、类型错误、数量超限或包含禁止字段的输出不得入库。
  - 技能标签、优势、发展方向 / 待验证项和项目亮点的证据覆盖率为 100%，每项至少包含 `source_field` 和 `evidence_text`。
  - 简历原文没有的信息保持未知或标记为待验证，画像中不出现敏感属性推断和无证据的人格、心理、诚信或潜力结论。
  - 求职者无法读取其他求职者画像；HR 无法读取未申请其本人创建岗位的候选人画像。
  - 同一求职者基于新简历或重新生成画像后产生新的画像版本，旧版本不被覆盖，默认读取最新成功版本。
  - 画像结果可被匹配模块读取，匹配结果能够追溯到使用的职业画像版本和简历版本。
  - 模拟首次 AI 生成失败时系统最多自动重试 1 次；再次失败后可人工重试，使用预置画像时页面和数据均明确标记为演示兜底。

### 3.5 人岗匹配

功能名称：人岗匹配

功能目标：计算候选人与岗位的匹配度，帮助 HR 快速筛选，并解释匹配理由、能力缺口和风险点。

功能要求：

- MVP 级别：
  - 求职者主动点击“申请岗位”后创建 `application` 关系；P0 不支持 HR 邀请候选人。
  - 输入已确认的职业画像、岗位画像、求职意向和对应申请关系。
  - 固定使用技能匹配、经历匹配、项目相关度和求职意向 4 个评分维度。
  - 固定权重为技能匹配 30%、经历匹配 25%、项目相关度 35%、求职意向 10%。
  - 每个维度先归一化为 0-100 分，再按固定权重计算 0-100 总匹配分。
  - 学历、学校和毕业年份仅在 JD 明确提出对应要求时，作为经历匹配维度的子项参与评分；系统不得自行推断学校偏好。
  - 缺少必备技能或未满足 JD 明确要求时只扣分并形成缺口提示，不自动淘汰或拒绝候选人。
  - LLM 只负责从简历和 JD 提取标准化标签，并根据后端评分结果生成推荐理由、能力缺口和风险解释；不得修改分数、权重或排序。
  - 输出四个维度分、总匹配分、推荐理由、能力缺口和风险点。
  - 支持 HR 查看候选人排序。
  - 匹配规则固定为 `match_rule_v1`，每条结果保存规则版本和四个维度分。
  - 学历、学校和毕业年份允许按上述规则参与评分；性别、年龄、出生日期、民族、婚育、宗教、健康、残障、照片和外貌等属性完全排除。
  - P0 使用 SQLite 保存申请关系和匹配结果，不引入向量数据库、机器学习排序模型或独立推荐服务。

- 平衡级别：
  - 覆盖 MVP 级别全部要求。
  - 支持求职者主动申请和 HR 邀请两种候选来源。
  - 可增加语义相似度辅助、岗位级权重配置、规则快照和更完整的证据引用。
  - 准备 30-50 个脱敏人工标注样例，比较系统排序与人工排序的一致率。
  - 仍由规则负责评分，LLM 只负责标签提取和结果解释，最终决策由 HR 作出。

验收标准：

- MVP 级别：
  - 每个候选人对每个岗位生成 0-100 匹配分。
  - 每条结果包含技能、经历、项目和求职意向 4 个 0-100 维度分，按 30% / 25% / 35% / 10% 权重计算的总分可复算且结果一致。
  - 每条匹配结果至少包含 3 条推荐理由和 2 条风险或缺口。
  - 智能招聘工作台能按匹配分降序展示候选人。
  - 缺少必备技能的候选人仍保留在排序中，结果标记对应缺口，不产生自动淘汰状态。
  - 每条匹配结果记录 `match_rule_v1`，刷新或重新查询后规则版本和分数保持一致。
  - 性别、年龄、出生日期、民族、婚育、宗教、健康、残障、照片和外貌等属性不会出现在评分输入、理由或风险点中。
  - 使用首批 2 类岗位和 10-20 个脱敏人工标注样例完成排序人工检查。

### 3.6 智能面试提问

功能名称：智能面试提问

功能目标：根据简历、岗位和匹配结果生成可追溯的个性化题目，避免泛化题库；P2 在同一功能内扩展基于候选人回答的动态追问。

功能要求：

- 当前选择：采用 MVP 基线，并加入平衡级的 HR 精细调整、题目数量调整、草稿保存、确认版本回退和修改记录能力；不选择题目难度分层、历史题目模板缓存、模型二次内容审核和企业级审计系统。
- MVP + 已选平衡能力：
  - 仅当岗位画像已确认、候选人已申请该岗位且匹配结果有效时生成面试题。
  - 默认生成 5 道题，HR 可在 5-8 道范围内调整本次生成数量。
  - 题目固定覆盖项目经历、岗位技能和能力缺口 3 类，不要求难度分层。
  - 每道题保存题目正文、题目类别、考察能力、提问依据、来源类型和简短来源引用。
  - 来源类型只允许简历字段、岗位要求和匹配缺口。
  - HR 可选择、删除、手动编辑或单题重新生成题目，调整结果自动保存为当前草稿，并在调整后确认整套题目。
  - 只有已确认的题目集才能进入候选人面试会话。
  - 后端使用确定性规则拦截敏感或歧视性题目；P0 不增加第二次模型审核。
  - 每个申请关系保留一份当前可编辑草稿；每次确认整套题目时基于草稿创建不可变的已确认版本。
  - 支持从已确认版本继续创建新草稿，并支持将历史确认版本恢复为当前版本；回退不覆盖或删除已有确认版本。
  - 保存当前草稿、历次确认版本、题目来源、当前生效版本和修改记录。
  - 题目选择、删除、手动编辑、单题重新生成、整套确认和版本回退均记录操作者、操作时间、动作类型和变更前后摘要。
  - P0 题目生成先采用同步请求，前端显示加载状态；API 和数据库预留 `pending`、`running`、`completed`、`failed`、`fallback` 状态。
  - 实际测试中若生成经常超过 15 秒或出现请求超时，再升级为后台任务加前端轮询，P0 不提前引入消息队列。
  - 生成失败时可重试或显式使用对应岗位类别的预置题目，预置结果必须标记为 `fallback`。
  - P2 动态追问不进入当前验收；后续必须复用题目安全、来源引用和会话状态约束，不另建提问入口。

验收标准：

- MVP + 已选平衡能力：
  - 默认可生成 5 道题，HR 选择 6、7 或 8 道时，后端按所选数量返回；小于 5 或大于 8 的请求被拒绝。
  - 每套题覆盖项目经历、岗位技能和能力缺口 3 类，且每道题包含考察能力和提问依据。
  - 默认 5 道题时至少 4 道具有有效来源；生成 6-8 道时，至少 80% 的题目能关联到简历字段、岗位要求或匹配缺口。
  - 固定脱敏样本由产品 / HR 人工检查题目与来源引用是否真实相关，不以模型自评替代验收。
  - 包含敏感属性或歧视性内容的题目会被后端规则拦截，不能进入 HR 确认列表。
  - HR 可以完成题目选择、删除、手动编辑、单题重新生成和整套确认。
  - 编辑页面刷新或重新登录后仍可恢复当前未确认草稿；未确认题目不能被候选人面试会话读取。
  - 确认后刷新页面仍能读取当前生效版本，已确认版本内容不会因后续草稿编辑而改变。
  - 至少产生 2 个已确认版本后，HR 可以恢复上一确认版本，恢复后候选人读取到的是恢复后的当前版本。
  - 选择、删除、编辑、单题重新生成、确认和回退后均能查询对应修改记录，记录包含操作者、时间、动作类型和变更前后摘要。
  - 删除草稿或回退版本不会删除已有确认版本和历史修改记录。
  - 同步生成期间页面显示加载状态；成功、失败和预置兜底分别落入 `completed`、`failed`、`fallback` 状态。
  - 模拟真实生成失败时，可以重试或使用明确标记的预置题目继续流程。
  - 对固定测试样本记录生成耗时；若多次超过 15 秒或出现请求超时，则触发升级为后台任务加轮询的技术决策。

### 3.7 岗位能力试炼

功能名称：岗位能力试炼

功能目标：用岗位任务验证候选人的真实岗位能力。P0 形成单个轻量任务闭环，P2 在同一功能内扩展场景化、多步骤模拟，不另建入口。

功能要求：

- 当前选择：采用 MVP 任务内容和最终决策边界，并加入平衡级的任务重新生成、一次重交、截止时间、有限附件、AI 参考评分、完整状态流转和文件安全能力；不保存任务历史版本，也不保存首次提交内容。
- 根据已确认的岗位画像生成 1 个轻量任务，任务包含背景、要求、交付物和评分标准。
- AI 生成后由 HR 确认发布；发布前 HR 可以修改或重新生成任务，重新生成直接覆盖当前草稿，不保存任务历史版本。
- 候选人可提交文本、HTTP / HTTPS 链接，或 PDF、DOCX、TXT、PNG、JPG 附件；单个附件不超过 10MB。
- 外部链接只保存和展示，后端不主动访问、抓取或执行链接内容。
- 默认只允许提交一次；HR 可以在截止时间前为当前申请开放一次重新提交。重新提交后仅保留最终提交内容，被覆盖的旧附件需要删除，不保留首次提交内容或完整提交版本历史。
- HR 可以设置截止时间；截止后未提交的任务过期，并禁止首次提交和重新提交。P0 不支持截止后延期、重新开放或补交。
- 任务状态采用 `draft -> published -> in_progress -> submitted -> evaluated`，未按期提交的任务进入 `expired`；HR 在截止前开放重交后，任务回到 `in_progress`。
- AI 按评分标准输出维度参考分、表现评价、证据和能力缺口，所有分数必须标记为“AI 参考评分”。
- HR 可以阅读 AI 评价和参考分，但不能修改 AI 原始评价；是否进入真人面试仍必须由 HR 独立决定。
- 任务生成失败时可重试或使用明确标记的预置任务，候选人的真实提交和评价仍进入正常主流程。
- 最终任务提交及 AI 评价进入 AI 面试证据链报告。

验收标准：

- 每个已确认岗位画像至少能生成 1 个任务，任务说明包含背景、要求、交付物和不少于 3 项评分标准。
- HR 可以修改或重新生成未发布任务，并完成确认发布；候选人不能读取 `draft` 状态任务。
- 发布前重新生成任务后只保留当前草稿，不提供历史任务版本查询或恢复。
- 候选人可以分别完成文本、HTTP / HTTPS 链接和允许类型附件的提交。
- 非允许类型、MIME 不匹配或超过 10MB 的附件被后端拒绝；合法附件只能由任务候选人本人和岗位创建 HR 读取。
- 系统只保存外部链接，不会因提交链接主动发起网络请求。
- 默认第二次提交被拒绝；HR 在截止前开放一次重交后可以再次提交，任务回到 `in_progress`，最终数据只展示第二次提交内容且被覆盖的旧附件已删除。
- 系统记录提交次数、首次提交时间和最终提交时间，但不能读取被覆盖的首次提交正文、链接或附件。
- 设置截止时间后，未提交任务到期进入 `expired`，后端拒绝新的首次提交和重新提交。
- 任务可以按 `draft`、`published`、`in_progress`、`submitted`、`evaluated` 正常流转，并能处理 `expired` 分支。
- 每份已提交任务可生成包含维度参考分、评价、证据和能力缺口的结构化 AI 评价，页面明确展示“AI 参考评分”。
- HR 不能修改 AI 原始评价或参考分，但可以独立保存是否进入真人面试的最终决定。
- 模拟任务生成失败时，可以重试或使用明确标记的预置任务继续主流程。
- 报告中能够引用最终任务提交和 AI 评价证据。

### 3.8 面试会话与记录

功能名称：面试会话与记录

功能目标：统一管理设备检测、面试会话、逐题回答、实时文字稿、答后确认和数据生命周期；P2 在明确授权后扩展短期音视频保存与回放。

功能要求：

- 当前选择：默认申请摄像头和麦克风权限，语音回答为主，回答过程中实时转写，文字输入兜底；设备体验采用平衡级方案，数据保存、实时通信和事件记录保持 MVP 边界。
- 候选人逐题查看面试题并回答。
- 进入面试前检测摄像头、麦克风和浏览器 ASR 能力，并提供重新授权入口。
- 摄像头只用于浏览器本地实时预览，不录制、不上传、不保存，也不参与 AI 评分或可信面试判断。
- 摄像头或麦克风拒绝授权时，页面说明受影响能力，并允许降级为仅语音或纯文字回答，不能阻塞面试主流程。
- P0 不设置强制回答倒计时，不自动提交或终止超时回答。
- 每题回答文字稿通过 REST API 自动保存到后端，刷新或短暂中断后可以恢复。
- 会话支持 `created`、`in_progress`、`paused`、`submitted`、`expired` 和 `abandoned` 状态。
- 会话首次开始回答时进入 `in_progress`，并从该时刻起固定 24 小时有效；暂停、刷新或重新进入不会停止或重置计时。
- 超过 24 小时仍未最终提交的会话进入 `expired`。过期会话只能查看已保存内容，不能继续回答或提交；候选人仍具备面试资格时需要重新创建会话。
- 逐题保存和最终提交使用后端状态校验与幂等键，避免重复回答、重复提交和重复生成报告。
- 只记录面试开始、结束、逐题保存和最终提交等必要事件，不记录可信面试风险事件，不输出风险结论。
- P0 不使用 WebSocket 或 SSE，不保存任何音频和视频。
- P2 音视频保存与回放不进入当前验收；后续必须先明确授权、保存期限、对象存储、访问控制和删除机制。

验收标准：

- 候选人可以完成至少 5 道题的回答流程。
- Chrome / Edge 可以完成设备检测、权限申请、摄像头本地预览和语音转写；不支持 ASR 的浏览器仍可使用文字回答。
- 摄像头或麦克风拒绝授权后，页面给出可解释提示，并能继续完成剩余回答和最终提交。
- 页面刷新或短暂中断后，可以恢复已自动保存的逐题文字稿。
- 面试会话可以正常暂停、恢复、提交，并能处理过期和主动放弃状态。
- 会话首次进入 `in_progress` 时正确保存 `started_at` 和 24 小时后的 `expires_at`；暂停或重新进入后 `expires_at` 保持不变。
- 到达 `expires_at` 后，未提交的 `in_progress` 或 `paused` 会话自动或在下次访问时转为 `expired`，后端拒绝新的逐题保存和最终提交。
- 过期会话不会触发报告生成；重新参加面试时创建新的会话 ID，不复用或恢复旧会话。
- 重复逐题保存或重复最终提交不会产生重复回答、重复提交记录或重复报告任务。
- 系统只保存 `sessionId`、`questionId`、`startTime`、`endTime`、`submitTime`、确认后的文字稿和必要状态；后端不存在面试音频或视频文件。

#### P0 文字稿子能力

该子能力把候选人回答转成 HR 和 AI 可读文本，为报告评价和证据引用提供输入。

功能要求：

- 语音回答时使用浏览器 Web Speech API 在回答过程中实时生成临时文字稿。
- 每道题结束后，候选人可以确认或修改文字稿，确认后的版本作为报告输入。
- Web Speech API 不可用或转写失败时，允许直接输入文字或使用明确标记的备用文字稿。
- 不上传音频到后端，不引入云 ASR、音频临时存储或后台转写任务。

验收标准：

- Chrome / Edge 下能在回答过程中实时显示转写结果，并在每题结束后完成确认或修改。
- 每道题至少保存一份候选人确认后的文字稿记录。
- ASR 不可用或失败时，候选人可以通过文字输入继续完成面试并生成报告。
- 后端不接收或保存音频文件。

### 3.9 AI 面试证据链报告

功能名称：AI 面试证据链报告

功能目标：输出 HR 可读的结构化决策报告，把评分、回答证据、任务证据、匹配依据和成长建议串起来。

功能要求：

- MVP 级别：
  - 每次生成一个结构化报告实体，不分别调用模型生成两份报告。
  - 同一报告实体按权限提供 HR 版和求职者版两个视图。
  - HR 版包含总评分、维度评分、推荐结论、风险点、回答证据、任务证据和成长建议。
  - 求职者版包含其可见的优势、待改进项、回答与任务证据摘要和成长建议，不包含 HR 私有风险备注、决策备注或内部推荐结论。
  - 报告生成后进入 `pending_review`，仅 HR 可查看完整报告。
  - HR 确认后报告进入 `confirmed`，求职者才能查看求职者版；确认只控制发布，不修改 AI 原始内容。
  - 每个重要结论尽量绑定证据来源，AI 输出使用结构化格式约束。
  - 支持展开证据片段，并记录 AI 模型、Prompt 版本、生成时间和脱敏输入摘要。

验收标准：

- MVP 级别：
  - 每个完成面试和任务提交的候选人可生成 1 份报告。
  - 报告至少包含 4 个评分维度、3 条证据、2 条风险点、3 条建议。
  - 报告生成后状态为 `pending_review`，智能招聘工作台可查看 HR 版，求职者接口返回不可见状态。
  - HR 确认后状态变为 `confirmed`，求职者可读取求职者版，且无法读取 HR 私有字段。
  - HR 版和求职者版来自同一个报告 ID，公共评分与证据引用保持一致。

### 3.10 智能招聘工作台

功能名称：智能招聘工作台

功能目标：给 HR 提供统一筛选和决策入口。P0 完成岗位、候选人、报告和人工决策主流程，P1 在同一工作台扩展智能摘要、同岗对比和批量初筛。

功能要求：

- MVP 级别：
  - 展示 HR 发布的岗位列表。
  - 展示候选人匹配排序。
  - 可查看候选人报告。
  - 可标记是否进入真人面试。
- 平衡级别：
  - 覆盖 MVP 级别全部要求。
  - 支持筛选、搜索、状态过滤。
  - 支持候选人备注。
  - 支持简单统计，例如候选人数、平均匹配分、推荐进入面试人数。
  - P1 扩展能力不进入当前验收：招聘 Copilot 输出亮点、风险和追问建议；同岗候选人横向对比能力证据；校招场景批量导入、匹配、排序和分组。

验收标准：

- MVP 级别：
  - HR 能在一个页面完成候选人排序、报告查看和决策标记。
  - 每个候选人卡片至少展示姓名、岗位、匹配分、状态、报告入口。
  - 决策状态可保存，刷新后仍存在。
- 平衡级别：
  - 覆盖 MVP 级别全部验收标准。
  - 支持按状态和岗位筛选候选人。
  - HR 备注可保存、编辑、删除。
  - 工作台统计数据与候选人列表数量一致。

### 3.11 求职者成长中心

功能名称：求职者成长中心

功能目标：让求职者看到自己的画像、面试表现、能力短板和下一步改进建议，形成成长闭环；P1 在同一入口扩展学习路径、回答复盘和训练任务。

功能要求：

- MVP 级别：
  - 求职者可查看职业画像。
  - 可查看面试反馈和成长建议。
  - 展示适配岗位、优势、短板、改进方向。
  - P1 扩展能力不进入当前验收：根据能力缺口生成学习主题、练习任务和资源路径，并解释回答中的逻辑、表达和专业短板。

验收标准：

- MVP 级别：
  - 每个完成报告的求职者可查看 1 份反馈。
  - 反馈至少包含 2 条优势、2 条短板、3 条改进建议。
  - 求职者不能查看 HR 内部风险备注或决策备注。

### 3.12 多 Agent 协作面板

功能名称：多 Agent 协作面板

功能目标：在答辩和演示中清楚解释系统内部如何分工：解析、画像、匹配、面试、任务、报告各自由不同 Agent 或步骤负责。

功能要求：

- MVP 级别：
  - 面板基于后端固定 Orchestrator 和真实 `ai_runs` 记录，不使用前端伪造的运行状态。
  - 展示简历解析、职业画像、JD 解析、人岗匹配、智能提问、岗位任务和报告生成等固定工作流节点。
  - 每个节点展示运行状态、脱敏输入摘要、脱敏输出摘要、模型版本、Prompt 版本、耗时、错误信息和兜底来源。
  - 面板为只读能力，不提供修改节点结果、重排工作流或改变业务状态的操作。
  - 面板查询、渲染或单个节点记录缺失时，不阻塞简历、匹配、面试、任务或报告主业务闭环。

验收标准：

- MVP 级别：
  - 至少展示 7 个节点：简历解析、职业画像、JD 解析、人岗匹配、智能提问、岗位任务、报告生成。
  - 每个节点能展示 `pending`、`running`、`completed`、`failed` 状态；使用预置结果时额外显示兜底来源，不把 `fallback` 伪装成真实执行成功。
  - 页面展示的运行数据可以追溯到真实 `ai_runs` 记录，输入输出摘要不包含姓名、电话、邮箱等直接身份信息。
  - 模型版本、Prompt 版本和耗时字段可读取；失败节点能展示可解释错误。
  - 面板接口失败时主业务接口仍可正常完成，面板页面显示独立降级提示。
  - 演示数据可完整展示一条固定 Agent 工作流。

### 3.13 演示预置数据

功能名称：演示预置数据

功能目标：在 AI、ASR、网络或现场环境不稳定时，用预置岗位、简历、画像、匹配结果和报告保证演示不断链。

功能要求：

- MVP 级别：
  - 准备至少 1-2 类岗位的完整预置数据。
  - 包含岗位、简历、画像、匹配结果、面试题、任务、文字稿、报告。
  - AI 失败时允许切换到预置结果。

验收标准：

- MVP 级别：
  - 至少 2 个岗位、3 份候选人简历、3 份完整报告可用于演示。
  - 断网或 AI 失败情况下，智能招聘工作台和报告页仍可展示。
  - 预置数据能跑通 roadmap 演示顺序的关键页面。

## 6. 演示顺序

1. HR 注册并发布岗位。
2. 系统解析 JD 并生成岗位画像。
3. 求职者上传简历。
4. 系统生成候选人画像和匹配分。
5. HR 查看排序与推荐理由。
6. 系统生成个性化面试题。
7. 系统生成岗位能力试炼，用一个小任务验证候选人真实能力。
8. 候选人进入轻量面试，摄像头仅用于本地预览，以语音逐题回答并实时转写；设备或 ASR 不可用时降级为文字回答，同时提交岗位任务结果。
9. 每题结束后候选人确认或修改文字稿，系统保存确认后的版本供报告使用。
10. 系统给出 AI 面试证据链报告，并在求职者成长中心开放脱敏反馈。
11. HR 最终点击是否进入真人面试。

## 7. 演示兜底策略

- 主路径使用真实上传、真实解析、真实生成。

- AI 失败时展示可解释错误，允许切换到预置结果继续演示。
- ASR 失败时允许展示备用文字稿或手动输入文字稿。
- 岗位能力试炼生成失败时允许切换到预置试炼任务，但任务结果和 AI 面试证据链报告仍要能进入主流程。

## 11. MVP 与平衡级升级边界

| 决策项 | MVP 选择 | 平衡级选择 | 升级条件 |
|---|---|---|---|
| 架构 | FastAPI 模块化单体 | FastAPI + 后台任务队列 | AI 任务耗时明显影响体验 |
| 数据库 | SQLite 起步 | PostgreSQL | 进入真实多用户试用 |
| Agent | 手写固定工作流 | LangGraph 或状态机 | Agent 步骤和异常分支增多 |
| 面试与试炼 | 题目 + 岗位任务 + 摄像头本地预览 + 实时转写 + 文字兜底，不保存音视频 | 虚拟面试官 + 动态追问 + 短期音视频保存 | 需要更强演示沉浸感或音视频复查 |
| 文件 | 少存文件，默认不长期存视频 | 对象存储 + 签名 URL | 需要音频/视频复查 |
| 模型 | 低成本稳定模型 | 多模型适配和备用模型 | 主模型不稳定或效果不足 |
| 部署 | 固定 HTTPS 演示链接 | 更完整监控和告警 | 真实用户增长 |

## 13. P1 真人面试预约

功能目标：在 HR 基于完整上游评估结果决定候选人进入真人面试后，为求职者和企业提供正式线上或线下面试的基础预约闭环。P1 采用“HR 发送绑定申请预约链接 -> 候选人登录后查看指定主面试官档期 -> 自助选时 -> 系统锁定时间并发送已维护会议或地点邀请”的流程。该能力扩展真人面试衔接，但不替代 AI 模拟面试、岗位能力试炼、证据链报告或企业招聘决策。

建议版本归属：P1 下一阶段。原因是它能够自然延续当前核心闭环，但依赖完整上游评估结果、岗位创建 HR 授权、指定主面试官、基础档期、站内通知、会议或地点信息和审计能力，不应挤占当前 P0、3-4 周里程碑或比赛演示范围。

前置依赖：

- 候选人已完成人岗匹配、AI 面试、岗位能力试炼，并存在已确认 AI 证据链报告。
- 岗位创建 HR 作出进入真人面试决定，并为具体岗位申请生成 3 天有效的绑定申请预约链接。
- HR 发送链接前指定主面试官、线上/线下面试类型，并确保会议链接或线下精确地点已维护。
- 求职者、HR、主面试官和企业归属的访问边界；P1 首期不引入企业管理员。
- 主面试官一次性可预约时间段、预约状态与状态历史、站内通知和审计记录。
- 联系方式、会议链接和地点信息的最小化展示、确认后可见和敏感访问审计要求。

主要交付物：

- 绑定岗位申请的预约链接生成、撤回、3 天有效期和登录账号匹配校验。
- 指定主面试官、线上/线下面试类型、真实基础档期管理和时间段锁定。
- 候选人预约页的月历 + 最近可用时间列表、候选人已有预约冲突提示和不可泛筛选边界。
- 预约创建、确认、取消、改期、待补全、完成、候选人未到场、面试官未到场和状态历史。
- 站内通知、面试前 24 小时和 1 小时提醒、通知失败记录与重试。
- 人工维护的会议链接、企业/岗位级线下地点模板、到场说明和预约时联系方式确认。
- 轻量结构化真人面试报告、HR 确认发布、企业内部视图、求职者摘要视图和 AI 证据链报告引用。

验收标准：

- 未完成匹配、AI 面试、岗位试炼和已确认 AI 证据链报告的申请，岗位创建 HR 不能生成预约链接。
- 候选人只能使用绑定本人申请且未过期的预约链接；未登录需先登录，账号不匹配时拒绝访问。
- HR 发送链接前必须指定主面试官和线上/线下面试类型；候选人只查看该主面试官在邀请范围内的可用时间。
- 线上或线下预约均能完成“HR 发链接 -> 候选人选时 -> 系统锁定 -> 发送会议/地点邀请 -> 查看结果 -> 取消或改期 -> 完成或未到场 -> 报告发布”的已配置流程。
- 同一岗位申请首期只有一个有效预约；同一候选人和同一主面试官时间均不能重叠；重复请求不能创建重复预约。
- `pending_confirmation` 只用于预约后关键信息失效或撤回；6 小时未补齐时系统取消并释放档期。
- 取消、改期、未到场、报告发布和敏感信息查看均保留审计；通知失败不改变预约状态。
- 会议链接、联系方式和详细地点只向必要参与者在确认后展示；不默认暴露简历解析出的联系方式。
- 真人面试报告独立存在，AI 证据链报告只保留引用，不直接合并真人内容，也不反向更新 AI 匹配、推荐或能力画像。
- A/B 级规则冻结后才能进入接口、数据和页面设计，不以默认实现替代产品确认。

后续路线：

- P1 后增强：`.ics` 最小信息导出、邮件通知、线下地点文字信息增强和面试官规则推荐；这些能力不得反向扩大 P1 首期基础预约闭环。
- P2 独立能力：企业管理员、周期性排班规则模板、多轮面试、群面、多面试官面板、企业可配置录制和真人报告 PDF、CSV/Excel 导出。
