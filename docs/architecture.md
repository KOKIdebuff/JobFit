# HireLink 技术架构文档

## 1. 架构目标

在不引入过重基础设施的前提下，跑通 HireLink 的核心 AI 招聘闭环，并保留后续演进空间。

当前架构服务于比赛 / 演示 MVP：个人 3-4 周开发、尽量保留现有前端、优先控制成本、优先稳定展示。

## 2. 架构风格

- 前端保留现有 React / TanStack Start + Tailwind CSS 页面，避免大规模重写。
- 后端优先使用 Python FastAPI，承载业务 API、权限校验和 AI 工作流调度。
- 采用模块化单体架构，不使用 Kubernetes、复杂微服务和大型分布式架构。
- 前端和后端通过 REST API 解耦，前端不直接处理敏感业务规则。
- 模型、ASR、TTS、文件存储通过适配层封装，后续可以替换供应商。

## 3. 推荐技术栈

| 层级 | MVP 推荐 | 平衡级推荐 |
|---|---|---|
| 前端 | React / TanStack Start + Tailwind CSS | React + Tailwind CSS + 更完整状态管理 |
| 后端 | FastAPI | FastAPI + 后台任务队列 |
| 数据库 | SQLite | PostgreSQL |
| 认证 | FastAPI JWT + 基础角色权限 | FastAPI JWT + RBAC + 审计日志 |
| 文件存储 | 本地临时存储 / 只保存必要文本和元数据 | OSS / MinIO / Supabase Storage |
| 大模型 | 可切换模型接口（供应商待定） | 多模型适配层 + 备用模型 |
| ASR | 浏览器 Web Speech API（Chrome / Edge 优先） | 云 ASR 或 Whisper 服务 |
| TTS | 浏览器 Web Speech API 或暂不核心实现 | 云 TTS |
| 面试录制 | 浏览器 MediaRecorder 采集，默认不长期保存视频 | 音频 / 视频短期对象存储 |
| Agent 编排 | 手写固定工作流 Orchestrator | LangGraph 或自研状态机 |
| 部署 | GitHub 自动部署 + 固定 HTTPS 链接 | 前后端分离云部署 + 监控 |
| 日志监控 | 后端结构化日志 + 前端错误提示 | Sentry / 云日志 |

## 4. 系统分层

### 4.1 前端层

- 登录、注册、角色切换。
- 求职者端：简历、画像、反馈、轻量面试。
- HR 端：岗位、候选人、报告、决策。
- 管理端：用户与权限管理。
- 移动端和桌面端都需要可用，HR 工作台优先保证桌面体验。

### 4.2 后端 API 层

- 负责认证、权限、业务数据读写。
- 提供统一 REST API。
- 负责文件上传、状态查询、任务触发。
- 负责校验前端请求，不能只依赖前端隐藏页面做权限控制。

### 4.3 Agent 服务层

- 简历解析 Agent
- 职业画像 Agent
- 岗位解析 Agent
- 人岗匹配 Agent
- 面试题生成 Agent
- 面试评价 Agent
- 任务试炼 Agent

MVP 阶段由一个后端 Orchestrator 串起，不拆成独立微服务。每个 Agent 只负责明确任务，不做自由决策。

### 4.4 数据层

- SQLite 存结构化数据；后续可迁移到 PostgreSQL。
- MVP 默认只保存必要文本、结构化结果、回答文字稿和报告。
- 简历原文件可选保存，结构化文本必存。
- 音视频默认不长期保存，只保留必要元数据。
- 先不引入向量数据库，除非后续需要语义检索。

## 5. 核心数据流

```text
简历上传
 -> 文本抽取
 -> 结构化简历
 -> 职业画像
 -> 岗位 JD 解析
 -> 人岗匹配
 -> 面试题生成
 -> 轻量面试回答
 -> 答后 ASR 转写
 -> AI 评价报告
 -> HR 决策
 -> 求职者反馈
```

## 6. Agent 编排约束

- 采用“固定工作流 + 多个职责清晰的 Agent”，不采用完全自由决策的 Agent。
- 关键节点需要人工确认，例如 JD 解析结果、候选人报告、HR 最终决策。
- Agent 不允许自由修改关键业务状态，只能通过后端定义好的接口和状态流转执行。
- Agent 输出必须结构化，并进行格式校验。
- Agent 失败时优先返回可解释错误或备用结果，不让演示流程直接中断。

## 7. 关键技术决策

- API 先用 REST，避免过早引入复杂实时架构。
- LLM 输出必须受 JSON Schema 约束，保证结构稳定。
- 匹配分建议由规则或权重模型主导，LLM 负责解释，不负责裸打分。
- 面试评价默认展示理由，证据由后端保留，必要时支持展开查看。
- 设备检测和反作弊只做基础事件记录，不做强判定。
- 大模型、ASR、TTS、文件存储都要通过接口封装，避免后续供应商锁定。
- 主路径真实生成，演示时允许使用预置数据兜底。

## 8. 数据模型主实体

| 实体 | 作用 |
|---|---|
| users | 用户账号、角色、企业归属 |
| companies | 企业信息 |
| resumes | 简历原文与结构化结果 |
| jobs | 岗位与 JD 画像 |
| candidate_profiles | 职业画像 |
| match_results | 人岗匹配结果 |
| interview_questions | 面试题 |
| interview_sessions | 面试会话 |
| interview_answers | 回答记录和文字稿 |
| evaluation_reports | 评价报告 |
| feedback_records | 求职者反馈 |
| media_files | 音频 / 视频 / 附件元数据，不默认长期保存内容 |
| ai_runs | AI 调用记录、模型来源、输入摘要、输出结果和错误信息 |

## 9. 安全与隐私

- 必须做后端权限校验，不能只靠前端隐藏页面。
- 基础角色至少区分求职者和 HR。
- HR 只能访问授权范围内的岗位、候选人、回答文字稿和报告。
- 简历、回答文字稿、报告、音视频元数据都属于敏感数据。
- 简历、音视频、报告如需文件访问，应走私有访问或签名 URL。
- 敏感字段需要最小化暴露。
- AI 输出要保留来源和版本，方便追溯。
- 音视频默认不长期保存，降低隐私风险和存储成本。
- 管理员需要能够删除用户、岗位、简历和演示数据。
- 如果后续允许短期保存音频，需要补充过期删除和用户删除能力。

## 10. 部署建议

- 前端：Vercel / Netlify 或同类支持 GitHub 自动部署的平台。
- 后端：优先选择中国大陆可稳定访问的云平台、ECS + Docker，或其他可固定公开访问的平台。
- 数据库：MVP 可 SQLite 或 PostgreSQL；平衡级使用云 PostgreSQL。
- 文件：MVP 少存文件；平衡级使用 Supabase Storage、OSS 或 S3 兼容存储。
- CI/CD：GitHub Actions 或平台自带部署。
- SQLite 起步时，演示前需要支持手动导出数据库和预置数据备份。
- 访问：需要固定公开 HTTPS 链接，优先保证比赛评委访问稳定。
- 并发：当前不追求极端高并发，优先保证小范围演示稳定。

## 11. 待确认事项

- 是否已有云服务器或部署平台账号。
- 模型供应商未定，只要求模型接口可切换。
## 12. 设计原则

- 先保证闭环，再谈增强。
- 先保证可解释，再谈智能。
- 先保证稳定可演示，再谈复杂实时化。
- 核心业务数据由后端统一管理。
- AI 只辅助招聘判断，最终决定由 HR 作出。
- 高成本功能先使用可替换接口封装。
- 敏感数据默认少存、限权、可追溯。
- 避免过度设计：不上 Kubernetes、不拆复杂微服务、不做高拟真数字人。
